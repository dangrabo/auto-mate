# auto-mate — Build Phases

A slow, incremental build plan. `PLAN.md` says *what* we're building and *why*; this file says
*in what order* and *how we know each step works*.

## How to read this

- Each phase produces something **runnable and testable on its own**. We don't move on until the
  current phase works and is understood.
- Each phase lists: **Goal**, **Files**, **New concepts** (Python / tooling ideas introduced),
  **Done when** (the check that proves it works).
- Phases are roughly the same order as the pipeline in `PLAN.md` §3, built back-to-front where
  that's easier to test (e.g. read from GitHub before we write to it).

---

## Phase 0 — Project skeleton & tooling

**Goal.** An empty but real project: `uv` manages it, `ruff` lints it, the package imports, the
right things are gitignored.

**Files.**
- `pyproject.toml` (via `uv init`)
- `.gitignore` — `automate.db`, `.env`, `workspaces/`, `__pycache__/`, `.venv/`
- `.env.example` — documented keys, no values
- `src/automate/__init__.py` — empty, makes `automate` a package
- `src/automate/cli.py` — a stub `main()` that just prints "auto-mate alive"

**New concepts.** What `uv` is and does; `pyproject.toml`; the `src/` layout; what a "package"
is (`__init__.py`); console-script entry points; `ruff check` / `ruff format`.

**Done when.** `uv run automate` prints the stub line; `uv run ruff check .` passes.

## Phase 1 — Config

**Goal.** One typed settings object, loaded from `.env` exactly once, imported everywhere else.

**Files.**
- `src/automate/config.py`
- `.env` (real, gitignored) + additions to `.env.example`
- `tests/test_config.py`

**New concepts.** `pydantic-settings` (or a plain dataclass — we'll decide together);
environment variables; why "read env in one place" matters; type hints on a class; `pytest`
basics — test files, `assert`, fixtures.

**Done when.** A test constructs the settings from a sample env dict and reads
`settings.github_repo` etc.; missing required keys raise a clear error.

---

## Phase 2 — Database layer

**Goal.** A SQLite file with a `jobs` table and a `poll_state` row, created and migrated by
Alembic, readable/writable through SQLAlchemy.

**Files.**
- `src/automate/db/__init__.py`
- `src/automate/db/models.py` — `Job`, `PollState`
- `src/automate/db/session.py` — engine + `SessionLocal` factory
- `migrations/` — `alembic init`, edited env, first autogenerated migration
- `alembic.ini`
- `tests/test_models.py`

**New concepts.** ORM vs raw SQL; SQLAlchemy 2.0 `DeclarativeBase` / `Mapped` / `mapped_column`;
what an "engine" and a "session" are; enums in the DB; Alembic — why migrations, `revision
--autogenerate`, `upgrade head`; using an in-memory SQLite DB for tests.

**Done when.** `uv run alembic upgrade head` creates `automate.db`; a test opens a session,
inserts a `Job(issue_number=1, ...)`, commits, queries it back, and a second insert with
`issue_number=1` fails the unique constraint.

## Phase 3 — GitHub client (read side only)

**Goal.** Ask GitHub for issues labelled `automate`, updated since a timestamp.

**Files.**
- `src/automate/github.py` — `GitHubClient` with `list_automation_issues(since)`
- `tests/test_github.py` — with mocked HTTP responses

**New concepts.** `httpx` (sync client for now); REST — URL, headers, auth token, query params,
JSON response; pagination via the `Link` header; `async def` vs sync (we'll write this sync
first, note where async comes later); mocking HTTP in tests (`respx` or `httpx.MockTransport`);
reading API docs.

**Done when.** A test feeds a canned GitHub JSON payload and gets back a clean list of small
`Issue` objects (number, title, body, updated_at, labels); a quick manual script prints real
issues from your target repo.

---

## Phase 4 — Poller

**Goal.** The 5-minute loop: read cursor → fetch issues → insert new `Job` rows → advance cursor.

**Files.**
- `src/automate/poller.py` — `poll_once(session, client)` and `run_poller()` loop
- `tests/test_poller.py`

**New concepts.** `asyncio` — the event loop, `async def`, `await`, `asyncio.sleep`; why the
loop is `async` even though the DB calls are sync; separating "do it once" (testable) from "do
it forever" (the loop); idempotency — running `poll_once` twice must not create duplicates;
transactions.

**Done when.** `poll_once` against a mocked client inserts exactly the new issues, skips ones
already in the DB, and moves the cursor to the newest `updated_at`. Running it twice in a row
changes nothing the second time.

---

## Phase 5 — Triage

**Goal.** One cheap LLM call that answers "does this ticket need code changes?" with a reason.

**Files.**
- `src/automate/triage.py` — `triage(issue) -> TriageResult`
- `tests/test_triage.py`

**New concepts.** The Anthropic SDK; `claude-haiku-4-5`; system vs user messages; asking for
**structured JSON output** and parsing it safely; `max_tokens` and why we cap it; keeping the
network call behind a function so tests can stub it; handling a malformed LLM response.

**Done when.** Given a "fix the typo in README" issue it returns `needs_code=True`; given
"what's our deploy schedule?" it returns `needs_code=False` with a reason. The parser rejects
junk instead of crashing.

---

## Phase 6 — Workspace / worktree management

**Goal.** Maintain a local clone of the target repo; create and destroy a per-job
`git worktree` on branch `automate/issue-<n>`.

**Files.**
- `src/automate/workspace.py` — `ensure_clone()`, `create_worktree(issue_number)`,
  `remove_worktree(issue_number)`
- `tests/test_workspace.py` — against a throwaway local git repo

**New concepts.** `subprocess` — running `git` from Python, capturing output, checking exit
codes, `asyncio.create_subprocess_exec`; what a git worktree actually is; `pathlib.Path`;
cleaning up resources even when something fails (`try/finally`); keeping all of this inside
`workspaces/` and never touching the parent repo.

**Done when.** A test creates a worktree from a scratch repo, sees the new branch and directory,
writes a file there, then `remove_worktree` leaves the clone clean with the branch gone.

---

## Phase 7 — The Claude runner

**Goal.** Spawn `claude -p` inside a worktree with a prompt built from the ticket; stream and
parse its output; enforce a timeout; kill it if it hangs.

**Files.**
- `src/automate/claude_runner.py` — `build_prompt(issue)`, `run_claude(worktree, prompt) -> RunResult`
- `tests/test_claude_runner.py` — prompt building tested directly; the subprocess mocked or run
  against a tiny fixture repo

**New concepts.** `asyncio.create_subprocess_exec` with pipes; `--output-format stream-json` and
reading it line by line as it arrives; `asyncio.wait_for` for timeouts; terminating a child
process; the difference between "Claude failed" and "our code failed"; prompt construction as
plain string building.

**Done when.** `build_prompt` produces the expected text for a sample issue; a real run in a
fixture repo (one trivial ticket) leaves a commit on the branch; a fake hanging process is
killed at the timeout and reported as a failure, not a crash.

---

## Phase 8 — GitHub client (write side) + PR creation

**Goal.** Push a branch and open a PR; add/remove labels; comment on an issue.

**Files.**
- `src/automate/github.py` — add `create_pull_request`, `add_label`, `remove_label`,
  `create_comment`
- `src/automate/pr.py` — `open_pr_for_job(job)` = push branch + create PR, returns the URL
- `tests/test_pr.py`

**New concepts.** `POST` requests with a JSON body; GitHub's create-PR and labels endpoints;
`git push` from `subprocess` with a token in the remote URL (and keeping it out of logs); mapping
one job to `Closes #<n>` in the PR body; error handling on 4xx/5xx.

**Done when.** Against a real test repo: a manually created local branch is pushed and a PR
appears with the right title, body, and `Closes #`. Label add/remove works.

---

## Phase 9 — Worker (the state machine)

**Goal.** Tie phases 5–8 together: take one `queued` job and drive it to `pr_open` (or
`needs_human` / `failed`), recording every transition.

**Files.**
- `src/automate/worker.py` — `process_one_job(session)` and `run_worker()` loop
- `tests/test_worker.py` — each transition tested with the external calls stubbed

**New concepts.** Modelling a state machine in plain code (no library); making each step
**resumable** — safe to re-run after a crash; `attempts` and a retry cap; resetting orphaned
`running` jobs on startup; catching **specific** exceptions and moving the job to `failed`
instead of killing the process; structured logging.

**Done when.** A stubbed happy path takes a job `queued → running → pr_open`. A triage
"no code" result ends at `needs_human` with an issue comment. A forced failure increments
`attempts` and requeues, then escalates to `needs_human` after the cap. Restarting mid-run
resets the job to `queued`.

---

## Phase 10 — CLI entrypoint & running both loops

**Goal.** `uv run automate` starts the poller and the worker together and shuts down cleanly.

**Files.**
- `src/automate/cli.py` — real `main()`: check migrations, launch both tasks with
  `asyncio.gather`, handle Ctrl-C
- `tests/test_cli.py` (light)

**New concepts.** Running multiple `asyncio` tasks concurrently; `asyncio.gather` /
`asyncio.TaskGroup`; graceful shutdown on `SIGINT`; a startup check that the DB is migrated;
what "one process, two loops, one DB" looks like when it's all together.

**Done when.** Start it against a real test repo, label an issue `automate`, and within a poll
cycle a PR appears. Ctrl-C stops both loops without a traceback.

---

## Phase 11 — Label mirroring & hardening

**Goal.** Reflect job status onto the issue as `automate:<status>` labels; back off on GitHub
rate limits; tidy logging and errors.

**Files.**
- small additions across `worker.py`, `github.py`, `poller.py`
- `tests/` updates

**New concepts.** Keeping a read-only mirror in sync without ever reading state back from it;
respecting `Retry-After` / secondary-rate-limit responses; exponential backoff; a final review
against the CLAUDE.md conventions and `PLAN.md` guardrails.

**Done when.** Moving a job through the pipeline visibly relabels the issue at each step; a
simulated 403 rate-limit response makes the client wait and retry instead of failing.
